Proposal · revision 2Android UI qualityNovember 2026

Emulator screenshots that fail only when the UI changed

This plan makes instrumented screenshot tests on an emulator stable enough to be a required PR check. It's also simple enough that any developer can add one in about 15 minutes. The core is one pinned, CPU-rendered emulator with a written determinism contract. A JVM lane takes the screenshots that don't need a device, so the emulator lane stays fast and cheap.

Illustration of a typical false failure. Nothing in the app changed, but the status bar clock moved on by a minute. System UI demo mode removes this whole class of failure, and the rest of this plan handles the other sources of flakiness the same way.

The ask
  • Make emulator screenshot tests a required PR check, built on Google's testing-setup Android skill (updated 28 Oct 2026) and Dropshots 0.6.0.
  • Choose option B (two lanes) from the costed comparison below. Option A uses the same emulator design and only changes the shard count, so it stays available.
  • Ship a developer kit so adding a test means one Gradle plugin line, one rule and ./shots new.
  • Fund 7 weeks for 1 engineer, plus part-time design-system review. Week 1 is a measurement spike that decides go or no-go.
01 · Analysis

Why device screenshot tests flake

An instrumented screenshot is the product of the app plus everything around it: the emulator binary, system image, GPU path, system UI, clock, locale, navigation mode and timing. Teams usually give up on device screenshots because one of these changed and nobody could tell which. Every source below can be controlled, and this plan controls all of them in code.

02 · Source of record

What Google's testing-setup skill prescribes

The android/skills testing-setup skill is Google's testing playbook for coding agents. It was last updated on 28 October 2026, and the official screenshot testing docs link to it. It names Dropshots for instrumented screenshots and tells you when a device is required. It doesn't cover emulator determinism, so the contract in section 05 is this team's own design, built on top of it.

"If instrumented screenshot tests are requested, install Dropshots."testing-setup · Step 3

"You need a device for screenshot tests when verifying interaction with the system UI (examples: edge-to-edge rendering, notifications, picture-in-picture)"testing-setup · Step 12

"Install the com.dropbox.dropshots plugin in the module and a Dropshots() JUnit Rule."testing-setup · Step 13

This plan also follows these skill rules:

  • Keep the existing test stack.
  • Don't upgrade AGP as part of screenshot setup; make it a separate decision.
  • Never combine the legacy screenshot plugin and AGP test suites in one module.
  • Use DI fakes for loading, error and offline states.
  • Use DeviceConfigurationOverride to simulate window sizes and font scales (Step 11).
  • Keep end-to-end tests to about 5% of all tests.
  • Ask before documenting the testing strategy. Update AGENTS.md if it exists; otherwise write docs/testing.md and link it from a new AGENTS.md.
03 · Options

Three ways to run screenshot tests on an emulator, costed

All three options use the same determinism contract and developer kit. They differ in how many screenshots go through an emulator and whose hardware runs it. Every default below is an assumption to be replaced by week-1 measurements. Edit any value and the table recalculates.

OptionWall time / runCI minutes / run$ / monthSystem UI coverageWho maintains the emulator
A · Every screenshot on the pinned emulator, sharded–––All shots, at full fidelityUs. The highest load, with the most captures exposed to flakiness
B · Two lanes (recommended): device shots on the emulator, the rest on JVM–––Every screen that depends on system UIUs, at a small scale. The JVM lane adds an alpha tool to track
C · Every screenshot on a device farm (Firebase Test Lab, emulator.wtf)–––All shotsThe vendor, but we can't pin their image. Goldens must be recorded on the farm, and queue time is extra

Formulas:

  • A: each shard pays for a build and a boot. The wall time adds the captures split across shards.
  • B: the device lane and the JVM lane run in parallel, so the wall time is the slower of the two.
  • C: one build on our runner, plus device-minutes on the farm, with one setup minute per shard.

The default prices are placeholders: a 4-core Linux runner and about $1 per virtual-device hour. Check them against current GitHub and Firebase pricing.

Why B wins with these defaults: the emulator only runs the screens a device is needed for. That roughly halves CI minutes compared with A, and it shortens PR feedback without lowering fidelity where fidelity matters. If the spike shows emulator captures are much cheaper than assumed, moving to A is a change to the shard count, not a redesign.

04 · Proposal

Option B: the emulator lane, plus a JVM lane that keeps it small

05 · Robustness · our design

The determinism contract for the emulator lane

There are four layers. Each one removes a class of false failures, and each is enforced by a script or a rule rather than by convention. When the environment is wrong, the run fails with "environment drifted" before any pixels are compared, so nobody has to dig through 300 diff images to find the cause.

Device

Same inputs give the same pixels

  • One AVD, defined by a config.ini checked into git: 1080×2400 at 420 dpi, hw.keyboard=yes, SwiftShader, no cameras, forced cold boot.
  • A default;x86_64 system image at API 35 or 36, whichever matches targetSdk. Never an -atd image.
  • The emulator build and system image are downloaded by URL and verified by sha256 from emulator.lock, then cached by the lock file's hash. Nothing comes from the runner's preinstalled SDK.
  • Before tests run, the lock is checked against the emulator version, the image revision and ro.build.fingerprint.
  • Linux x86_64 runner with KVM. One emulator per CI job, because the Dropshots tasks call adb without choosing a device.

System

Nothing outside the app changes

  • At boot:
    • Animation scales set to 0, font scale 1.0, en-US, Etc/UTC, 3-button navigation.
    • hide_error_dialogs 1, svc power stayon true, keyguard dismissed.
    • Spell checker off, IME suppressed.
    • A check that no ANR dialog is showing.
  • Per test: demo mode on (12:00, full battery, separate Wi-Fi and mobile broadcasts, notifications hidden), then a 300 ms wait for it to settle. It exits after the test.
  • Night mode is set with cmd uimode night yes|no before the activity launches, then reset.

App

Inputs are fixtures, not live data

  • A Hilt test runner. @TestInstallIn swaps in fake repositories, a fixed Clock and a fake image loader.
  • UI state comes from a shared :fixtures module per feature, used by both lanes, so the device and JVM shots show the same state.
  • The Compose mainClock is paused and advanced by a fixed amount. Bundled fonts only.
  • No Test Orchestrator in Lane B. Each capture starts a fresh ActivityScenario, and this avoids a reported storage-permission issue in the shared Downloads folder (Dropshots #74).

Capture and compare

Strict, with no retries on mismatch

  • Stable capture: take full-screen screenshots until two in a row are identical (up to 6 tries, 100 ms apart). If the screen never settles, the failure is reported as infrastructure, not pixels.
  • Dropshots' default comparison: SimpleImageComparator(maxDistance = 0.004f) and CountValidator(0). Any looser threshold needs a written reason.
  • recordOnFailure = false, so a crash screen can never become a golden. Before recording, existing goldens are deleted so that orphaned images disappear.
  • Mismatches are never retried. Quarantine needs an issue link and an expiry date.
06 · Developer experience

Any developer can add a screenshot test in 15 minutes

Adoption fails when every team has to learn the determinism contract. In this plan the contract is built into a small kit: developers write content and a fixture, and the kit handles everything else. Most developers will only ever write Lane A previews.

Adding an emulator screenshot

  1. Apply the plugin once per module. Add id("example.screenshots.device") to the module's build.gradle.kts. It brings in Dropshots, the Hilt runner, the kit library and safe defaults.
  2. Scaffold the test. Run ./shots new feature:checkout CheckoutScreen. It creates the test class with DeviceShotRule and a fixture stub, with a reason placeholder to fill in.
  3. Fill in the content and run it. ./shots verify feature:checkout boots an emulator if none is running. On a Mac the result is advisory, and the first run reports "reference missing" as expected.
  4. Open the PR and add the record-shots label. CI records on the pinned emulator and pushes the goldens to your branch. The bot comments with the images, a design-system owner approves, and you merge.

Definition of done for a screenshot test

  • The test is in Lane A, unless the screen depends on system UI. Lane B tests have a specific reason.
  • State comes from a named fixture in the feature's :fixtures module. No network access, no real clock.
  • The test covers light and dark if the screen draws behind the system bars.
  • Names describe the state (loaded_dark), not an index. Dropshots rejects duplicate names.
  • Goldens were recorded by CI, not locally, and a design-system owner approved them.

// core/screenshot-testing/src/main/kotlin/com/example/testing/DeviceShotRule.kt
@Retention(AnnotationRetention.RUNTIME)
@Target(AnnotationTarget.CLASS)
annotation class DeviceScreenshot(val reason: String)

class DeviceShotRule(testInstance: Any) : TestRule {
  private val instrumentation = InstrumentationRegistry.getInstrumentation()
  private val args = InstrumentationRegistry.getArguments()

  // Dropshots 0.6.0: the Gradle plugin uses the *test* APK id for its device folder, but the
  // runtime defaults to the *app* id, so record and pull miss in app modules (dropbox/dropshots#115).
  // Point both at the test APK's folder.
  private val shotDir = File(
    Environment.getExternalStoragePublicDirectory(Environment.DIRECTORY_DOWNLOADS),
    "screenshots/${instrumentation.context.packageName}",
  )
  private val dropshots = Dropshots(
    recordScreenshots = File(shotDir, ".isRecordingScreenshots").exists(),
    rootScreenshotDirectory = shotDir,
  )
  val compose = createEmptyComposeRule()

  private val chain = RuleChain
    .outerRule(HiltAndroidRule(testInstance))
    .around(SystemUiFreeze())
    .around(compose)
    .around(dropshots)

  override fun apply(base: Statement, description: Description): Statement = chain.apply(base, description)

  fun capture(name: String, group: String, night: Boolean = false, content: @Composable () -> Unit) {
    // Must be set before launch so enableEdgeToEdge() picks matching system-bar icons.
    shell("cmd uimode night ${if (night) "yes" else "no"}")
    compose.mainClock.autoAdvance = false
    // HiltTestActivity lives in :core:screenshot-testing's debug source set and calls enableEdgeToEdge().
    ActivityScenario.launch(HiltTestActivity::class.java).use { scenario ->
      scenario.onActivity { it.setContent { AppTheme { content() } } }
      compose.mainClock.advanceTimeBy(1_000)
      compose.waitForIdle()
      dropshots.assertSnapshot(stableScreenshot(), name, group)
    }
  }

  private fun stableScreenshot(): Bitmap {
    UiDevice.getInstance(instrumentation).waitForIdle()
    var previous = instrumentation.uiAutomation.takeScreenshot()
    repeat(5) {
      SystemClock.sleep(100)
      val next = instrumentation.uiAutomation.takeScreenshot()
      if (next.sameAs(previous)) return next
      previous = next
    }
    throw IllegalStateException("INFRA: screen never settled; not a pixel failure")
  }

  private inner class SystemUiFreeze : ExternalResource() {
    override fun before() {
      val expected = args.getString("deviceShots.fingerprint")
      val onCi = args.getString("deviceShots.ci") == "true"
      if (expected != null && Build.FINGERPRINT != expected) {
        val msg = "Environment drifted: ${Build.FINGERPRINT} != $expected"
        check(!onCi) { msg }
        Log.w("DeviceShots", "$msg. Local results are advisory.")
      }
      shell("settings put global sysui_demo_allowed 1")
      demo("enter")
      demo("clock -e hhmm 1200")
      demo("battery -e level 100 -e plugged false")
      demo("network -e wifi show -e level 4")
      demo("network -e mobile show -e datatype none -e level 4")
      demo("notifications -e visible false")
      SystemClock.sleep(300)
    }
    override fun after() {
      demo("exit")
      shell("cmd uimode night no")
    }
  }

  private fun demo(command: String) =
    shell("am broadcast -a com.android.systemui.demo -e command $command")

  private fun shell(cmd: String) {
    // Read to EOF so the command finishes before the test continues.
    ParcelFileDescriptor.AutoCloseInputStream(instrumentation.uiAutomation.executeShellCommand(cmd))
      .use { it.readBytes() }
  }
}

// build-logic/convention/src/main/kotlin/DeviceShotsConventionPlugin.kt
// Registered as id "example.screenshots.device"
class DeviceShotsConventionPlugin : Plugin<Project> {
  override fun apply(target: Project) = with(target) {
    pluginManager.apply("com.dropbox.dropshots")   // 0.6.0, pinned in libs.versions.toml
    extensions.configure<DropshotsExtension> {
      recordOnFailure.set(false)   // never record a crash dialog as a golden
    }

    pluginManager.withPlugin("com.android.application") {
      extensions.configure<ApplicationExtension> {
        defaultConfig.testInstrumentationRunner = "com.example.testing.HiltTestRunner"
        testOptions.animationsDisabled = true
      }
    }
    pluginManager.withPlugin("com.android.library") {
      extensions.configure<LibraryExtension> {
        defaultConfig.testInstrumentationRunner = "com.example.testing.HiltTestRunner"
        testOptions.animationsDisabled = true
      }
    }

    val libs = extensions.getByType<VersionCatalogsExtension>().named("libs")
    dependencies {
      add("androidTestImplementation", project(":core:screenshot-testing"))
      add("androidTestImplementation", libs.findLibrary("hilt-android-testing").get())
      add("kspAndroidTest", libs.findLibrary("hilt-compiler").get())
    }
  }
}

#!/usr/bin/env bash
# ./shots: the one command for device screenshots.
#   ./shots new    <module> <ScreenName>   scaffold a test class and fixture stub
#   ./shots verify <module> [gradle args]  compare against goldens (advisory off CI)
#   ./shots record <module>                re-record goldens (CI only; use the record-shots label)
set -euo pipefail
source ci/emulator/emulator.lock
cmd=${1:?usage: ./shots new|verify|record <module>}; module=${2:-app}; dir=${module//://}
shift $(( $# >= 2 ? 2 : $# ))

args=(
  -Pandroid.testInstrumentationRunnerArguments.annotation=com.example.testing.DeviceScreenshot
  -Pandroid.testInstrumentationRunnerArguments.deviceShots.fingerprint="$EXPECTED_FINGERPRINT"
)
[[ "${CI:-}" == "true" ]] && args+=(-Pandroid.testInstrumentationRunnerArguments.deviceShots.ci=true)

case "$cmd" in
  new)
    exec ci/shots/scaffold.sh "$dir" "${1:?ScreenName}" ;;
  verify)
    ci/emulator/boot.sh --reuse
    ./gradlew ":$module:connectedDebugAndroidTest" "${args[@]}" "$@"
    echo "Diffs: $dir/build/test-results/dropshots/" ;;
  record)
    [[ "${CI:-}" == "true" ]] || { echo "Goldens are recorded on CI. Add the 'record-shots' label to your PR."; exit 1; }
    ci/emulator/boot.sh
    find "$dir/src/androidTest/screenshots" -name '*.png' -delete 2>/dev/null || true   # drop orphaned goldens
    ./gradlew ":$module:recordDebugAndroidTestScreenshots" "${args[@]}" ;;
  *) echo "unknown command: $cmd"; exit 2 ;;
esac

actual=$(a getprop ro.build.fingerprint | tr -d '\r')
[[ "$actual" == "$EXPECTED_FINGERPRINT" ]] || { echo "::error::image drift: $actual"; exit 1; }

Exit code 75 means an infrastructure failure, and CI retries the boot once. Exit code 1 means drift and fails immediately. The download URLs and checksums get filled in during week 1 and change only through a reviewed upgrade PR (see the runbook).

name: device-shots
on:
  pull_request:
    types: [opened, synchronize, reopened, labeled]
  schedule: [ { cron: "0 3 * * *" } ]     # nightly false-failure tracking on main

permissions:
  contents: read
  pull-requests: write

jobs:
  changes:                                 # always runs, so the required check never sits "pending"
    runs-on: ubuntu-24.04
    outputs: { ui: ${{ steps.f.outputs.ui }} }
    steps:
      - uses: actions/checkout@v4
      - id: f
        uses: dorny/paths-filter@v3
        with:
          filters: |
            ui:
              - '**/src/main/**'
              - '**/src/androidTest/**'
              - '**/build.gradle.kts'
              - 'gradle/libs.versions.toml'
              - 'build-logic/**'
              - 'ci/emulator/**'
              - '.github/workflows/device-shots.yml'

  verify:
    needs: changes
    if: needs.changes.outputs.ui == 'true' || github.event_name == 'schedule'
    runs-on: ubuntu-24.04
    timeout-minutes: 40
    strategy:
      fail-fast: false
      matrix: { shard: [0, 1] }            # one emulator per job: Dropshots' adb calls don't pick a device
    steps:
      - uses: actions/checkout@v4
        with: { lfs: true }
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: 17 }
      - uses: actions/cache@v4
        with: { path: .cache/emu, key: "emu-${{ hashFiles('ci/emulator/emulator.lock') }}" }
      - name: Enable KVM
        run: |
          echo 'KERNEL=="kvm", GROUP="kvm", MODE="0666", OPTIONS+="static_node=kvm"' \
            | sudo tee /etc/udev/rules.d/99-kvm4all.rules
          sudo udevadm control --reload-rules && sudo udevadm trigger --name-match=kvm
      - uses: gradle/actions/setup-gradle@v4
      - name: Boot pinned emulator (one retry, infrastructure only)
        run: ci/emulator/boot.sh || { [ $? -eq 75 ] && ci/emulator/boot.sh; }
      - name: Verify
        env: { CI: "true" }
        run: |
          ./shots verify app \
            -Pandroid.testInstrumentationRunnerArguments.numShards=2 \
            -Pandroid.testInstrumentationRunnerArguments.shardIndex=${{ matrix.shard }}
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: shots-${{ matrix.shard }}
          path: |
            **/build/test-results/dropshots/
            build/emulator.log
            build/logcat.txt

  gate:                                    # make THIS the required check
    needs: [changes, verify]
    if: always()
    runs-on: ubuntu-24.04
    steps:
      - run: '[[ "${{ needs.verify.result }}" =~ ^(success|skipped)$ ]]'

  record:
    if: github.event.action == 'labeled' && github.event.label.name == 'record-shots'
    runs-on: ubuntu-24.04
    timeout-minutes: 60
    steps:
      - id: app                            # an App token, so the pushed commit re-triggers CI
        uses: actions/create-github-app-token@v1
        with: { app-id: "${{ vars.SHOTS_APP_ID }}", private-key: "${{ secrets.SHOTS_APP_KEY }}" }
      - uses: actions/checkout@v4
        with: { ref: "${{ github.head_ref }}", token: "${{ steps.app.outputs.token }}", lfs: true }
      # ...same java / cache / KVM / gradle / boot steps as verify...
      - run: ./shots record app
        env: { CI: "true" }
      - name: Push goldens to the PR branch
        run: |
          git config user.name "shots-bot"
          git config user.email "shots-bot@users.noreply.github.com"
          git add -A -- ':(glob)**/src/androidTest/screenshots/**'
          git commit -m "Re-record device screenshots" || exit 0
          git push

PRs from forks can't use the record label, because secrets aren't available to them. A maintainer records on a branch in this repository instead. .gitattributes puts **/src/androidTest/screenshots/**/*.png in LFS.

## Screenshot tests
Full guide: docs/testing.md. Base skill: `android skills add testing-setup`.

- Default to Lane A (JVM): put `@PreviewTest` + `@ScreenMatrix` or `@ThemeVariants`
  in `src/screenshotTest/kotlin`. Run `./gradlew testScreenshotTestDefaultDebugTestSuite`.
- Use Lane B (emulator) only when the screen depends on system UI: edge-to-edge or insets,
  system-bar contrast, notifications, picture-in-picture, WebView, SurfaceView.
  - Scaffold with `./shots new <module> <Screen>`. Use `DeviceShotRule`.
  - `@DeviceScreenshot(reason = "...")` is required; name the system-UI dependency.
  - State comes from the feature's `:fixtures` module. Never hit the network or the real clock.
- Never record Lane B goldens locally. Ask for the `record-shots` PR label.
- Never raise a Dropshots threshold without a comment explaining why.

This follows the skill's final step: update AGENTS.md if it exists, or create it and link to docs/testing.md. Coding agents then add tests the same way people do.

08 · Workflow

Golden lifecycle

  1. Developer changes UI. Lane A runs locally in seconds. ./shots verify gives an advisory look at Lane B on a local emulator.
  2. PR opens. The gate check runs the emulator lane if UI paths changed. On a mismatch, the bot comments with reference, actual and diff images.
  3. The change is intended. The author adds the record-shots label. CI deletes the old goldens, records new ones on the pinned emulator and pushes a commit to the branch, and the push re-runs gate.
  4. Review. CODEOWNERS on **/screenshots/** and **/reference/** requires a design-system owner's approval. Code and images are reviewed in the same PR.
  5. Merge and monitor. A nightly run on main records the false-failure rate per capture and per run, and posts to the team channel if it's not zero.
09 · Operations

Running the emulator

Upgrading the image (quarterly, or when targetSdk changes)

  1. Open a branch and update the URLs and checksums in emulator.lock, plus API if needed.
  2. Run the record workflow. Every Lane B golden changes in one commit, together with the new EXPECTED_FINGERPRINT.
  3. A design-system owner reviews a sample of the diffs. Expect broad sub-pixel changes and look for layout changes.
  4. Run 10 cold-boot verify runs on the branch. Merge only if every run is clean.
SymptomAction
Boot timeout (exit 75)CI retries automatically. If it repeats, check KVM on the runner and look in emulator.log
"image drift" or "emulator version drift"Something bypassed the lock. Check the cache key and the SDK path
"INFRA: screen never settled"A running animation or a looping loader. Check the fixture and pause the clock
Diff only in the status barDemo mode didn't apply. Check logcat for the SystemUI broadcast
Empty diff artifactThe Dropshots folder doesn't match. Make sure the test uses DeviceShotRule

Owner: one named engineer for the contract, the lock file and the nightly report, with a second engineer as backup. They expect about 2 hours a month after rollout.
